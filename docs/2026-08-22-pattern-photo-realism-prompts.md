# Real-photo pattern rendering — photo-realism pass for the 3 pilot references

Phase 1 of the real-photo pattern plan (see the plan approved this session,
also summarised in `garment-photo.js`'s "Real-photo pattern rendering" block
comment). These 3 prompts turn the WebGL-mesh grey pilot renders into
photorealistic reference photos for the peak lapel jacket
(`jacket-sb-peak-flap`) — the seed images live in
`images/styleBuilder/pattern-seeds/`:

- `grey-plain-pinstripe.png`
- `grey-twill-chalkstripe.png`
- `grey-hopsack-windowpane.png`

**Critical: these must be EDITS of the exact seed image, not fresh
generations** — same discipline as prompt #8 in
`docs/2026-08-17-bespoke-spec-image-prompts.md`. A fresh text-to-image pass
gives a different pose every time; the whole point of seeding from the WebGL
mesh is that its lapel/collar bend is already the geometry this session spent
weeks getting right. Feed the actual PNG into Nano Banana Pro (or whichever
model tests best) as the base image and ask it to edit that image.

What the first pass got right, worth keeping: it correctly flattened the
WebGL seed's dramatic directional lighting into soft, even studio lighting —
the actual functional requirement below, not just a style preference — and
it preserved the pose and (real) button positions exactly.

## Why even, flat lighting is a hard requirement here — not a style choice

Confirmed by testing `garment-photo.js`'s new recolour function
(`recolourPatternPhoto`) against both the raw WebGL pilots and a synthetic
evenly-lit test image: the recolour step reads a photo's luminance to decide,
per pixel, whether it's looking at ground cloth or overlay stripe/check, then
maps each to the cloth's real colour. Fed the raw WebGL pilot directly, this
mis-fired — the pilot's strong directional Lambert shading (bright highlight
top-left fading to near-black at the collar recess) swings luminance across a
wider range than the actual ground/overlay difference, so the classifier
read "brightly lit" as "overlay" and "in shadow" as "ground," regardless of
the real pattern. Fed a synthetic image with the same soft, even lighting
this app's existing garment photos already use, it worked correctly on the
first try (verified against 4 cloths spanning stripe, windowpane and a plain
no-overlay cloth).

In short: **the SAME "soft even studio lighting, no hard highlights" rule
that already governs every other garment photo in this app
(`docs/2026-08-17-bespoke-spec-image-prompts.md`'s output spec) is now also
a functional requirement for this recolour step to work, not just a house
style match.** A dramatically top-lit result will produce visibly wrong
colours at runtime, not just look inconsistent next to the other photos.

## Output specs (match the existing garment photos exactly)

- Portrait, aspect ratio ≈ 4:5, at least 1600px on the long edge (matching
  `jacket-sb-peak-flap.webp`'s own proportions — the seed image is already
  this shape, so an edit should preserve it automatically).
- Pure flat white background, RGB 255 255 255 — the build pipeline keys the
  background out by flood-fill, same reasoning as every other garment photo.
- Soft, even studio lighting, no hard highlights, no strong directional
  shadow — see above for why this one is load-bearing here specifically.
- Visible woven cloth grain is fine and expected (real cloth has texture) —
  just don't let it read as a strong secondary light/dark banding on top of
  the actual ground/overlay colours; keep grain subtle relative to the
  pattern itself.
- Every outer edge (lapel roll-line, collar notch, sleeve outline, hem) must
  stay a clean, smooth, tailored line — no fraying, pinking, or rope/cord
  texture. Confirmed necessary, not just tidy: the first generation run
  applied "fabric texture" right at the silhouette boundary and came back
  looking like raw-cut, unfinished cloth (see Status above).

## The 3 prompts

Each one is an edit of its matching seed file. All three ask for the same
treatment — only the pattern-specific description changes.

### 1. Plain weave, pinstripe — `grey-plain-pinstripe.png`

```
Edit this exact photograph. Keep the pose, garment shape, silhouette,
buttons, and the bend of the lapel/collar/sleeve pattern exactly as they
are — do not regenerate the garment or change its cut in any way. Replace
only the rendering style: turn this into a photorealistic studio product
photograph of real woven wool cloth, plain weave, with a fine grey
pinstripe. Add authentic fabric texture — visible thread weave, subtle
natural fibre irregularity — but keep it understated, not a strong
secondary pattern of its own, and confine it to the cloth's face. Every
outer edge — the lapel roll-line, collar notch, and sleeve outline — must
stay a clean, smooth, precisely tailored line: no fraying, no pinking-shears
texture, no rope or cord texture, no raw or torn-looking cloth anywhere on
the silhouette boundary. Light the whole garment with soft, even
studio lighting, no hard highlights and no strong directional shadow —
flat, even illumination across the entire garment, matching commercial
ghost-mannequin product photography. Keep the background pure flat white.
Do not alter the pose, crop, proportions, or the pattern's bend at the
lapel and collar.
```

## After generating: check before batch-processing the rest of the 20

Per the approved plan, don't run all 20 pattern types through the WebGL →
AI-edit pipeline yet — check these 3 results first:

1. **Even lighting check (the load-bearing one)** — eyeball the result:
   does the lapel/collar area look meaningfully brighter or darker than the
   chest/body, independent of the actual cloth pattern? If yes, the
   recolour step will misread it (see above) — re-prompt emphasising flat
   lighting even harder, or add an explicit negative instruction ("no
   vignette, no spotlight, uniform brightness top to bottom").
2. **Clean-edge check** — zoom into the lapel roll-line, collar notch, and
   sleeve outline. Any fraying, pinking, or rope/cord texture there means
   re-prompting with the edge instruction above pushed harder, not
   proceeding (see Status above — this is exactly what went wrong on the
   first pass).
3. Save the result into `images/styleBuilder/` (not `pattern-seeds/` — that
   folder is the WebGL grey seeds, not the photorealistic output) using the
   naming convention `jacket-sb-peak-flap__<weave>-<pattern>.png`, e.g.
   `jacket-sb-peak-flap__plain-pinstripe.png`.
4. Add an entry to `PATTERN_SOURCES` in `tools/build-garment-assets.js`
   (already implemented, currently empty — see that file's comment just
   above the `SOURCES` map): `"jacket-sb-peak-flap__plain-pinstripe": {
   file: "jacket-sb-peak-flap__plain-pinstripe.png", twoTone: true }`, then
   run `node tools/build-garment-assets.js`. The `twoTone: true` flag is
   required — it routes the photo through `normaliseLuminanceTwoTone`
   instead of the single-tone `normaliseLuminance` every other garment
   photo uses, which keeps the ground/overlay bands at the fixed absolute
   levels `recolourPatternPhoto` expects (see that function's own comment
   in `garment-photo.js`); the plain `normaliseLuminance` would collapse
   them into one tone.
5. Add the resulting key to `PATTERN_PHOTO_KEYS["jacket-sb-peak-flap"]` in
   `garment-photo.js` (currently an empty object — every entry here is a
   no-op today, by design, until a real photo backs it) and the recolour
   path picks it up automatically; no other code changes needed.
6. Render a cloth from that pattern bucket in the Cloth Room / Bespoke Spec
   drawer and confirm the recoloured result shows the cloth's actual ground/
   overlay colours, correctly bent at the collar, next to a plain cloth
   (still on the old tile-composite path) to confirm nothing regressed
   outside this pattern's scope.

Once those 3 look right and the recolour step confirms them correctly,
generate the remaining 17 pattern types the same way (WEAVE_GROUNDS x
WEAVE_OVERLAYS minus the 3 done here, restricted to the 20 combinations that
actually occur in `cloth-data.js` — see the plan for that list).
